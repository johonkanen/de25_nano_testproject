# Plan for 2026-10-17: FPGA updates over the network

Goal: change the FPGA from the network - the fabric without rebooting
Linux, the HPS side with a controlled reboot and automatic fallback.

## The two parts of the FPGA (HPS-first boot)

| part | lives in | what it holds | changed by | Linux reboot? |
|---|---|---|---|---|
| **core** (`de25_nano.core.rbf`) | SD card FAT, `/lib/firmware`, QSPI copy at `0xC00000` | all fabric logic: register file, blinkers, fan controller | `fpga-reload` (works today, ~2 s) | **no** |
| **phase 1** | QSPI `0x200000` | HPS I/O, DDR I/O, SPL | JTAG today; RSU (step 2) | yes - the SDM restarts the HPS |

Day-to-day FPGA changes only need the core path. RSU is for HPS-side
changes (HPS IP, I/O, DDR, Quartus version) and boot software.

one by one (`docs/linux_boot.md`, Known gaps):

| changed | still hangs? |
|---|---|
| ATF 2.14.1 -> 2.12 | yes |
| HPS-first -> FPGA-first | yes |
| QSPI disabled in the Linux DT | yes |

the one working `reboot` (2026-10-16 ~22:50) started from a **power
cycle**. Hypothesis: after a JTAG load the SPL came over JTAG and the SDM
has nothing to restart the HPS from.

## Step 1 - core updates over the network, no reboot

Working today: `fpga-reload`, the kernel FPGA manager + overlay, the core
in `/lib/firmware`, U-Boot's preboot core loader.

1. **Build identity.** A core only loads on a phase 1 with the same periphery.
   - [x] `make_jic.sh` writes a manifest next to the core
         (`de25_nano.core.json`): build id, core SHA-256, and a periphery
         hash instead of a phase-1 hash - the phase-1 bitstream differs
         between two builds of the same periphery (182 bytes of per-build
         hashes) and the SDM loads the new core on the old phase 1 anyway
         (tested). The periphery hash covers the fitter's pin table
         (`.pin`, which names the Quartus version and device) and the HPS
         and EMIF `.ip` files
   - [x] the design exposes the build id on register 19
         (`write_build_id.sh` stamps the Unix time) - read back after a load
2. **Reload through `fpga_access`** - the only process touching LWH2F.
   - [x] a `reload` operation: pause register traffic, load the core
         (overlay on `/fpga-region`), check the board id and build id,
         write back the registers the load reset, resume
   - [x] replaces `fpga-reload`'s SIGSTOP of every `/opt/de25web` process
         (kept only for when the GUI isn't running)
3. **`POST /api/fpga`** (token-protected, like `/api/update`)
   - [x] upload a bundle: core + manifest + SHA-256
   - [x] refuse a core whose periphery hash differs from the installed one
   - [x] keep the previous core; load the new one; verify
   - [x] on any failure reload the previous core
   - [x] on success also write the card's copy, so the next boot uses it
         (`/boot` is normally unmounted; mounted just for the write)
   - [x] U-Boot's preboot falls back to the QSPI core when the card's core
         reads but does not load
4. **Tools and GUI**
   - [x] `linux/tools/deploy_fpga.py` (like `deploy_web.py`)
   - [x] an "FPGA core" card in the GUI next to "GUI release" (GUI 1.4.0)
5. **Tests**
   - [x] reload loop: 100 of 100 over `/api/fpga/reload`, 2.13-2.14 s each,
         blinker mode kept, Linux and the GUI kept running
   - [x] wrong-periphery and truncated cores refused (409) before anything
         is touched
   - [x] corrupt core with a matching manifest: **hangs the SDM** (load never
         returns, JTAG times out; power cycle). The SHA-256 check is the
         guard; register traffic now stays paused for the whole load (it
         used to expire after 120 s), and a timed-out request is no longer
         resent by the client
   - [x] interrupted install: `de25_nano.core.pending` -> the previous core
         is put back at the next start (on the board)
   - [x] power cut while the card copy is written: the copy is fsynced as
         `.new` and renamed, so the card keeps the old or the new core; with
         the card core missing U-Boot loaded the QSPI copy (power cycle,
         on the board)
   - [x] end to end: a fresh build (1792218111, same periphery hash) went
         over the network with `deploy_fpga.py` in 2.13 s, card copy written
   - [x] fan duty and blinker mode are written back after a reload
         (`fpga_access.py`), the temperature loop carries on

Note: a full core reload pauses LWH2F and the console for ~2 s. Partial
reconfiguration (`docs/partial_reconfiguration_plan.md`) would keep the
rest of the fabric running, but is not needed to update without a reboot.

## Step 2 - remote system update (phase 1, with a reboot)

From `docs/remote_system_update_plan.md`, adapted to HPS-first. Depends on
step 0: RSU ends in an SDM-driven reboot.

1. [x] **Linux sees the QSPI flash**: the garbled JEDEC read (`90 5d 8c`,
       is `20 bb 18` - shifted by one bit) was the clock, not the read
       delay: the dtsi says 200 MHz, the SDM gives the controller 500 MHz,
       so the flash ran at ~250 MHz. With `&qspi_clk` at 500 MHz the probe
       is clean and the QSPI core copy (1 MB) reads back identical, with
       read-delay 0..3; at the wrong clock read-delay 3..4 passed the id
       read but bulk reads differed every time.
       `CONFIG_INTEL_STRATIX10_RSU=y`: built in; its probe fails (`getting
       RSU status -14`, SDM error 0xc) until the flash has an RSU layout
2. [ ] **RSU flash layout** with `quartus_pfg`: factory image, application
       slots, decision firmware + SPT/CPB tables. HPS-first slots are small
       (~0.4 MB phase 1) + one U-Boot each; each slot's matching **core**
       must travel with it (in QSPI next to the slot, or on the card keyed
       by build id)
3. [ ] the SPL loads the U-Boot of its own slot (replaces the fixed
       `0xA00000` copy)
4. [ ] `librsu` / `rsu_client` (altera-fpga/intel-rsu) on the board
5. [ ] boot confirmation: a new slot counts as good only once the GUI,
       LWH2F and the core check pass; otherwise the watchdog falls back
6. [ ] upload API + `deploy_rsu.py` + fault tests
